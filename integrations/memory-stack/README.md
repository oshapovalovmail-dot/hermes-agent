# Honcho / OpenViking / оба с локальным FRIDA

Единая точка установки дополнительных систем памяти для **этого форка Hermes**.
Режимы: `honcho`, `openviking`, `both` (оба). В режиме `both` обе системы получают
завершённые ходы через штатный механизм `memory.providers`; отдельный дублирующий
писатель или MCP для этого не нужен. Встроенные `MEMORY.md` / `USER.md` сохраняются.

Установка предназначена для нового изолированного каталога. Она не переносит
историю из работающих хранилищ, не меняет активные профили, не перезапускает ботов,
не создаёт cron и не включает автосинхронизацию исходников. Состояние выбранных
сервисов остаётся отдельно от репозитория. Не запускайте установщик с каталогом
действующего Hermes или существующей базы данных.

## Что устанавливается

- **Всегда:** FRIDA ONNX INT8 CPU и проверенные файлы опубликованной модели.
- **Honcho:** PostgreSQL с pgvector, Redis, HTTP API и отдельный процесс deriver;
  наш exact-tokenizer patch и native Honcho plugin для Hermes.
- **OpenViking:** HTTP-сервис со своим постоянным хранилищем, конфигурацией FRIDA
  и LLM; exact-token caller adapter и native plugin с отдельным external-Compose
  подключением без запуска host-сервиса при отказе.
- **Оба:** одна копия FRIDA, оба backend и оба native plugin. Внешние tools
  поиска/чтения/записи сохраняются; доступность tools не подменяет проверку
  автоматического сохранения и вывода памяти.

Это интеграция операторского Hermes, а не описание серверной архитектуры Jeeves.
Обычный upstream Hermes документирует один внешний provider; режим `both`
требует реализации ordered multi-provider fan-out из этого форка.

## Требования

- Linux или macOS, Docker Engine / Docker Desktop с Compose v2.
- Python 3.12 или новее и Git на машине подготовки.
- Свободные loopback-порты для FRIDA и выбранных HTTP-сервисов; PostgreSQL/Redis
  не требуется публиковать на хост.
- Место для опубликованной модели, образов, сборки и постоянных данных. Размер
  модели и образы — разные расходы; холодная сборка требует больше места, чем
  последующий запуск.
- **LLM:** OpenAI-compatible endpoint, поддерживающий Chat Completions и
  структурированные ответы, доступная модель и действующий ключ с квотой.
  FRIDA заменяет эмбеддинги, но не генеративную модель, которая извлекает память,
  строит представления и отвечает на reasoning-запросы. Такие LLM-вызовы могут
  тарифицироваться выбранным провайдером.
- Установленный Hermes из этого форка. Не устанавливайте серверные зависимости
  Honcho / OpenViking в окружение работающего агента.

Ключ передаётся **путём к локальному закрытому файлу**, не значением в аргументе
команды. Не вставляйте его в README, `config.yaml`, командную строку, Git или чат.
Создавайте файл своим обычным защищённым способом; файл должен быть обычным, а не
symlink, и недоступным другим пользователям.

## Быстрый запуск

Из корня проверенного checkout этого форка (или распакованного исходного архива):

```bash
STACK="$HOME/.local/share/hermes-memory-stack"
LLM_BASE="https://api.openai.com/v1"
LLM_MODEL="gpt-4.1-mini"
LLM_KEY_FILE="$HOME/.tokens/memory-llm"

python3 integrations/memory-stack/install.py prepare \
  --provider both --root "$STACK" \
  --llm-base-url "$LLM_BASE" --llm-model "$LLM_MODEL" \
  --llm-api-key-file "$LLM_KEY_FILE"
python3 integrations/memory-stack/install.py up --root "$STACK"
python3 integrations/memory-stack/install.py check --root "$STACK"
```

Сначала создайте закрытый файл ключа. `LLM_BASE`/`LLM_MODEL` заменяются параметрами
вашего совместимого провайдера; пример не является предоставленным доступом.
В `--provider` выберите **`honcho` / `openviking` / `both`**. Параметр обязателен:
скрипт не выбирает дорогостоящую конфигурацию неявно.

`prepare` скачивает проверенные публичные артефакты, готовит плагины и настройки,
но не запускает контейнеры и не устанавливает server packages на хост. Каталог
`STACK` должен **не существовать**. Нельзя передавать каталог действующего профиля.
`up` собирает образы и запускает только этот проект, в том числе отдельный deriver
и миграцию Honcho. Все HTTP-порты опубликованы на `127.0.0.1`; PostgreSQL и Redis
на хост не опубликованы. Входящий API-доступ рассчитан на доверенного локального
оператора, а не на публичный многопользовательский сервер.

Порты по умолчанию: FRIDA **18501**, Honcho **18500**, OpenViking **18533**.
Если они заняты, передайте `--frida-port`, `--honcho-port`, `--openviking-port`
при `prepare`; используйте только параметры выбранных систем. Скрипт не убивает
чужие процессы и не переключается незаметно на другой адрес.

Проверка без работающей LLM-квоты — отдельный, явно неполный уровень:

```bash
python3 integrations/memory-stack/install.py check --root "$STACK" --storage-only
```

Его успешный JSON содержит `level: storage_only` и `derivation_verified: false`.
Обычный `check` возвращает ненулевой код, пока вывод памяти и причинно связанный
поиск/чтение не подтверждены. Синтетические факты сохраняются в отдельных
`probe-*` workspace/user scopes, не в рабочей памяти профиля.

После backend-проверок выполните [отдельную установку Hermes](ISOLATED-HERMES.md):
новые checkout, native PM runtime, selected Python environment и явный
`HERMES_BIN`, с сохранением созданного `STACK/hermes-home`. Один `HERMES_HOME`
не отделяет зависимости Python. Не используйте голый `hermes` из рабочего PATH.
Модель и авторизация основного агента настраиваются отдельно от LLM backend-памяти.

Остановить только созданную установку, сохранив постоянные данные:

```bash
python3 integrations/memory-stack/install.py down --root "$STACK"
```

`up --timeout` ограничивает ожидание готовности после сборки; холодная сборка может
занять больше времени. `check --timeout` задаёт срок вывода памяти для каждого
выбранного backend. По умолчанию — 180 и 120 секунд соответственно. `up` явно
пересоздаёт контейнеры своего проекта, не постоянные данные; это также перечитывает
закрытый файл ключа. Автозапуск, удаление данных и перенос существующего профиля
не выполняются.

Для проверенного локального кэша есть `--model-cache /absolute/model-directory`
и `--source-cache /absolute/provider-git-caches`; оба используются только для чтения.
Модельный кэш должен содержать три модельных файла и `LICENSE` из закреплённого
релиза. Source cache — каталоги `honcho`/`openviking` с нужными Git objects.
Без флагов исходники и веса загружаются явно при `prepare`, не при checkout.
Промежуточный каталог с неудавшимся `prepare` автоматически не стирается: используйте
новый каталог или разберите свою неполную подготовку, не подменяя marker.

## Контракт модели

Модель: [OShapovalov/frida-onnx-int8](https://huggingface.co/OShapovalov/frida-onnx-int8),
immutable revision `8c1ba6091bb395acff08e0921cd88fe9ad8a472b`.
Установщик потребляет готовый релиз; скачивание исходных FP32-весов, конвертация и
квантизация на каждой установке не нужны.

Проверяются размер и SHA-256 каждого используемого файла. Требуются граф
`frida-encoder-int8.onnx`, его соседний external-data файл
`frida-encoder-int8.onnx.data` и `tokenizer.json`. Не заменяйте только один файл
моделью из другого релиза.

Контракт обслуживания:

- 1536 измерений; masked mean pooling и L2-нормализация уже в графе;
- префикс `search_document: ` добавляется сервером;
- максимум 512 **полных** токенов, включая префикс и специальные токены;
- превышение отклоняется до inference, а не обрезается молча;
- contract ID: `frida-850455b6-document-mean-l2-frida512-overlap20-v2`.

Это сохранение установленного векторного пространства, а не утверждение о совпадении
с first-token pooling из исходной model card. Для подключения старого индекса
одного совпадения размерности недостаточно: отдельно проверяйте revision, pooling,
префиксы, токенизатор и результаты поиска. Установщик не мигрирует старые индексы.

## Идентичности и изоляция

Новая установка должна иметь собственный `HERMES_HOME`, workspace и assistant
identity. Honcho получает собственный `honcho.json` без fallback на глобальный
профиль; стратегия локальных сессий и префикс backend-сессии задаются явно.
OpenViking получает отдельный ovcli config с адресом своего сервиса и явным
`use_ovcli_config: true`. Режим `deployment: external-compose` читает только этот
файл, игнорирует чужие `OPENVIKING_*` connection overrides и не запускает host
OpenViking, если собственный backend недоступен. Для обоих
нужно создавать новые Hermes session IDs, а не копировать `state.db` другого бота.

Разные bot tokens и разные домашние каталоги сами по себе не доказывают раздельные
backend-сессии. Особенно важно не свести одинаковые Telegram DM keys двух ботов в
один Honcho session. При намеренном общем user/workspace доступ к историческим
воспоминаниям и изоляцию разговоров проверяют отдельно; этот сценарий не является
автоматическим переносом данных.

## Проверка результата: разные уровни

1. **Подготовка:** файлы модели проверены; закреплённые исходники/патчи применены;
   сформированы настройки только выбранных систем.
2. **Запуск:** контейнеры работают, HTTP-сервисы доступны на нужных loopback-портах.
3. **Эмбеддинги:** FRIDA сообщает весь ожидаемый контракт и реально возвращает
   конечные нормализованные 1536-мерные векторы; проверяется семантический контроль,
   а не только `/health`.
4. **Хранение:** тестовый текст/сообщение можно независимо прочитать после записи.
5. **Вывод памяти:** нормальная ingestion-цепочка обработала текст с помощью LLM;
   Honcho закончил очередь/сформировал вывод, а OpenViking закончил конкретный commit
   task без ошибки и создал производные данные. Затем поиск и чтение подтверждают
   именно тестовый результат.
6. **Hermes:** новый изолированный процесс загрузил выбранные providers/tools;
   завершённый ход реально сохранился и читается независимо из каждого backend.

Успешные пункты 1–4 не означают автоматически 5–6. В частности, прямое создание
готового conclusion проверяет хранение/поиск, но не работоспособность deriver.
Нулевой результат извлечения из произвольного текста допустим; для приёмочного
контроля используют специально заданный ясный синтетический факт.

Oracle обычного `check` намеренно узкий: английское утвердительное предложение
о предпочтении `cobalt blue` у конкретного нового `probe-*` проекта. Совпадение
слов в разных документах, другой субъект или отрицание не принимаются. Пересказ,
не попавший в эту консервативную грамматику, даёт неполную приёмку, а не ложный PASS;
это не универсальная оценка качества естественно-языковой памяти.

В OpenViking после commit активный `messages.jsonl` может опустеть: проверяйте
задачу commit и её архив/выходные документы, а не делайте вывод о потере истории
по одному пустому файлу. Счётчик commit без завершённой задачи не является PASS.

## Работа с существующим Hermes

Не копируйте весь каталог `integrations/` в `plugins/` и не устанавливайте поверх
неизвестной версии plugin. Используйте версии, восстановленные из manifest этого
же Git snapshot. Обычное обновление из plugin catalog может заменить наши патчи.

После подготовки нового профиля provision клиентских зависимостей и validation
выполняются через [native PM recipe](ISOLATED-HERMES.md) в отдельной установке.
`plugins validate --install-deps` не создаёт изолированную установку, а меняет
выбранное окружение; в recipe dependencies установлены до validation.
Не реконструируйте подготовленные plugins поверх: это удалит installer-owned
external-Compose patch. Серверный пакет OpenViking в окружении Hermes не нужен;
Honcho plugin требует совместимый SDK `honcho-ai>=2.2.0,<3`.

В YAML должны совпасть список providers, включённые plugins и отдельные backend
конфигурации. Режимы:

```yaml
# honcho
memory:
  provider: honcho
  providers: [honcho]
```

```yaml
# openviking
memory:
  provider: openviking
  providers: [openviking]
```

```yaml
# both
memory:
  provider: honcho
  providers: [honcho, openviking]
```

MCP — дополнительный интерфейс, не замена native capture. Не добавляйте второй
MCP/cron писатель для тех же ходов. Рабочий gateway не перезапускается установщиком;
его отдельно согласованное подключение проверяется в новой сессии после загрузки
нового профиля.

## Ошибки и восстановление

- **Порт занят:** выберите другой порт или отдельную машину. Не завершайте чужой
  процесс и не меняйте production-порт для освобождения значения по умолчанию.
- **SHA/размер не совпали:** установка прерывается. Не отключайте проверку;
  незавершённое скачивание нельзя считать готовым модельным кэшем.
- **FRIDA health 200, `model_loaded=false`:** модель не готова. Проверьте все три
  файла и contract metadata; не принимайте существование контейнера за readiness.
- **HTTP 400 `input_too_long`:** текст длиннее точного лимита. Honcho должен
  использовать поставленный tokenizer patch, OpenViking — startup adapter,
  оба — тот же `tokenizer.json`; нельзя
  «исправлять» проблему молчаливым truncation или увеличением объявленного лимита
  поверх реального лимита encoder.
- **HTTP 401/403 LLM:** проверьте endpoint, модель, локальный файл ключа и права.
  Не выводите ключ или полный environment в отчёт.
- **HTTP 429 / quota:** восстановите доступ/квоту у провайдера. Установка и
  доступные векторы при этом не доказывают вывод памяти; полной проверки PASS нет.
- **TLS:** используйте корректный доверенный CA bundle. Не отключайте проверку
  сертификатов.
- **LLM доступна на хосте, но недоступна из контейнера:** проверьте DNS и маршрут
  именно внутри выбранного backend. Docker Desktop может не иметь маршрута к
  IPv6-only endpoint, доступному macOS через VPN. Увеличение timeout и повторная
  отправка сообщения это не исправляют. Нужен endpoint, доступный непосредственно
  из контейнера; изменение глобальной сети Docker установщик не выполняет.
- **Неоконченное извлечение:** сначала читайте конкретную задачу и ошибки. Не
  отправляйте тот же текст повторно вслепую: обработка могла продолжиться после
  клиентского timeout.

Остановка сервисов должна сохранять постоянные данные. Удаление volumes, нового
профиля, ключей или history — отдельная явная операция владельца, не автоматическая
«починка». Не подключайте сюда Docker volumes работающих сервисов.

## Закреплённые версии

- Honcho Server **3.1.1**, Git `2ad56a4d715b015d744ea86f05a287069d264898`, с separately licensed exact-tokenizer patch.
- OpenViking Server **0.4.15**, hashed Python 3.12 lock и startup adapter.
  `max_input_tokens=2147483647` — только явный sentinel для обхода upstream
  приблизительного guard: adapter ограничивает каждый фактический запрос FRIDA
  512 точными токенами, делит исходный Unicode без потери символов и нормализует
  взвешенную сумму листьев один раз. Сам FRIDA лимит не увеличивается.
- FRIDA runtime — [`integrations/frida`](../frida/README.md); версии зависимостей заданы в `requirements-runtime.lock`, веса — в закреплённом HF-манифесте выше.
- Каталожные плагины — отдельные immutable commits и результирующие SHA-256 из `integrations/memory-providers/manifest.json`. Версия backend и версия плагина — разные контракты.
